# ADR-0008: Database Migration Governance — Alembic Replaces `create_all()`

## Status

Accepted.

## Context

Since the first bounded context was built, `app/main.py` called
`Base.metadata.create_all(bind=engine)` on every process start against
the real, on-disk `substationos.db`. This has two problems that grew
more serious as the number of bounded contexts (and tables) grew:

1. **No schema history.** `create_all()` only creates tables that don't
   yet exist — it never alters an existing table, never records what
   changed or when, and gives no way to move a database from one known
   schema version to another (forward or backward). By Milestone 12
   there are 18 tables across 9 bounded contexts (Project, Documents,
   Engineering Index, Proposed Claims, Review Workflow,
   Canonicalization, Graph Builder, Project Knowledge Graph, and the
   legacy Knowledge Graph tables), several with foreign keys between
   them — a change to any one of them had no mechanism to reach an
   existing database safely.
2. **Startup silently mutated schema.** A developer (or a deployment)
   starting the app against a database missing a table would have that
   table silently created at that moment, with no log, review, or
   record — indistinguishable from an intentional migration. This
   directly conflicts with CLAUDE.md §16 ("Data integrity — domain
   invariants are enforced in code, not assumed... bad data is
   rejected loudly at the boundary, never silently accepted") and with
   Milestone 12's own requirement that "production startup no longer
   relies on `create_all()`."

A migration framework was needed, but the repository already contains
locally-created, `create_all()`-built dev databases (including the
maintainer's own in-use `substationos.db`, which was locked by a
running process during this milestone's work) — any migration solution
had to be provably safe to adopt against an existing database, not
just against a fresh one.

## Decision

### 1. Alembic manages all schema lifecycle; `create_all()` is removed from application startup

`apps/backend/alembic.ini` and `apps/backend/migrations/` are the
single source of schema change going forward.
`Base.metadata.create_all(bind=engine)` is deleted from `app/main.py`
entirely (see [operational_reliability.md](../operational_reliability.md)).
A database that has not been migrated (`alembic upgrade head`) now
fails loudly at first query, which is the correct failure mode — not
silently patched into shape.

The one deliberate, narrowly-scoped exception: `tests/conftest.py`'s
`db_session` fixture still calls `Base.metadata.create_all()` against
a disposable, per-test, in-memory SQLite database. This is not
"normal startup" — it is test isolation infrastructure, rebuilt from
nothing on every test, and never touches a real schema. No other use
of `create_all()` remains anywhere in application code.

### 2. The connection string has one source of truth: `app.database.database.DATABASE_URL`

`alembic.ini`'s `sqlalchemy.url` is deliberately left unset.
`migrations/env.py` imports `DATABASE_URL` from
`app.database.database` at runtime and uses it directly — the exact
value the running application uses — so migrations and the application
can never point at two different databases by accident (CLAUDE.md §16,
Provider Independence: a single source of truth for infrastructure
configuration). A `SUBSTATIONOS_DATABASE_URL` environment variable
overrides this for a single Alembic invocation only (never read by the
application itself — see `.env.example`), so a migration can be
generated or tested against a scratch database without touching the
real one or editing code.

### 3. Baseline strategy: `alembic revision --autogenerate` against a fresh schema, adopted non-destructively via `alembic stamp head`

The first migration
(`migrations/versions/b3e2e0f30024_baseline_all_governed_tables.py`)
was generated by running `alembic revision --autogenerate` against a
throwaway, empty scratch SQLite database
(`SUBSTATIONOS_DATABASE_URL` pointed at a local scratch file, deleted
afterward) — never against the maintainer's real, in-use database.
Its `upgrade()` creates, and `downgrade()` drops, every one of the 18
tables `Base.metadata` currently declares, matching exactly what
`create_all()` used to build.

This gives three supported, explicitly documented workflows (see
[database_migrations.md](../database_migrations.md) for exact
commands):

- **Fresh database:** `alembic upgrade head` creates every table from
  nothing. Proven this milestone against a scratch SQLite file.
- **Existing, `create_all()`-built dev database:** `alembic stamp head`
  — a genuinely non-destructive operation that writes only a single
  `alembic_version` tracking row, touching no existing table — adopts
  an already-correct-shaped database under migration control without
  re-running any `CREATE TABLE`. Proven this milestone against a copy
  of an existing dev database.
- **Running the app:** requires `alembic upgrade head` (or `stamp
  head` for a pre-existing database) as a documented prerequisite;
  application startup performs no DDL of its own.

No migration in this baseline is destructive: the baseline only
creates tables, and its `downgrade()` only drops the same tables it
created — no existing table is altered or dropped as a side effect of
adopting Alembic.

### 4. The baseline includes the legacy Knowledge Graph tables, unchanged

`project_entities` and `entity_relations` (the legacy Knowledge Graph
tables — see [ADR-0009](0009-legacy-knowledge-graph-isolation.md)) are
included in the baseline migration alongside every governed table.
Removing legacy-table migration coverage was never requested and was
never how `create_all()` managed them (it always created all tables
from `Base.metadata` together, governed and legacy alike) — splitting
them into a separate migration history would be a speculative,
unrequested redesign, not a hardening change.

## Consequences

**Easier:**
- Schema changes now have a reviewable, ordered history
  (`migrations/versions/*.py`), each one a small, readable diff of the
  exact DDL it applies — matching CLAUDE.md §10's "small, atomic
  commits" for schema, not just code.
- A new environment (CI, a teammate's machine, a future staging
  deployment) reaches the correct schema with one documented command,
  not by hoping `create_all()` happens to run before anything queries
  the database.
- Rollback (`alembic downgrade`) is now possible and explicit, where
  `create_all()` offered none.

**Harder:**
- Every future model change now requires a matching migration —
  `migrations/env.py`'s model-import list must be kept in sync with
  `app/main.py`'s, a manual step (documented, not automated — see
  `database_migrations.md`) since no model-discovery mechanism exists
  in this codebase and building one is out of this milestone's scope.
- A developer who forgets to run `alembic upgrade head` after pulling
  a change that adds a migration will see a clear failure at first
  query, not a silently-patched schema — a deliberate trade of
  convenience for correctness.

## Rejected Alternatives

- **Keep `create_all()`, add manual `ALTER TABLE` scripts for changes.**
  Rejected: no tooling would track which scripts had already run
  against which database, reintroducing exactly the "no schema
  history" problem this ADR exists to solve, just spread across ad hoc
  files instead of one framework.
- **A different migration framework (e.g. a custom SQL-script runner).**
  Rejected: Alembic is the SQLAlchemy project's own migration tool,
  already compatible with `Base.metadata` with zero additional
  dependency-graph risk, and is the de facto standard for
  SQLAlchemy-based Python services — introducing a custom framework
  would be unjustified complexity for a problem Alembic already solves
  (CLAUDE.md §14, "do not introduce a new external dependency without
  a clear reason").
- **Force-migrate the maintainer's real, in-use `substationos.db`
  during this milestone.** Rejected: the file was OS-locked by a
  running process at the time, and even unlocked, mutating a live
  local database as a side effect of writing an ADR is exactly the
  kind of irreversible, unrequested action CLAUDE.md's "Executing
  actions with care" guidance warns against. Both supported workflows
  were instead proven against disposable scratch copies; the
  maintainer runs `alembic stamp head` against the real file
  themselves, on their own schedule, following
  `database_migrations.md`.
- **Drop the legacy `project_entities`/`entity_relations` tables from
  the baseline.** Rejected: they are still actively written by
  `app/services/knowledge_graph.py::ingest_document`, called from
  every document upload — dropping them from migration coverage would
  desynchronize the one part of the schema still under active write
  load. See ADR-0009.
